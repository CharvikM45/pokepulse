# Card metadata provider boundary

Documentation checked 2026-11-07. Neither provider is configured, selected or permission-approved for this application. No API keys were requested, accounts created, paid plan selected or real card images downloaded.

| Candidate | Current primary documentation                                                                                                                                                                                                                                                                                               | Implementation implication                                                                                                                                                                            |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TCGdex    | The [FAQ](https://tcgdex.dev/faq) describes keyless access and encourages response caching. It identifies known printing flags and ongoing work on more detailed variant data.                                                                                                                                              | A normal/reverse/holo flag is evidence to review, not a complete Master manifest. Keep unknown variants explicit and publish only curated, validated manifests. No image rights approval is inferred. |
| Scrydex   | [Authentication documentation](https://scrydex.com/docs/getting-started/authentication) describes a team, plan and API credentials. Its [image guidance](https://scrydex.com/docs/getting-started/best-practices) places responsibility for copyright permissions on the application user and recommends caching/fallbacks. | Keep credentials server-side, confirm account limits/terms before access, and treat image clearance independently from API access. No plan cost or artwork permission has been assumed.               |

`packages/domain/src/catalog/provider.ts` defines a metadata-only provider interface and a gated normalization boundary. It accepts a provider-specific set ID, not an arbitrary URL. A concrete vendor adapter must use a fixed reviewed host, bounded response size/timeouts and caching allowed by that provider's actual terms. Inventory, stock truth and retailer price services remain A-owned and are absent from this interface.

The permission reader is evaluated before and after the bounded async provider call. Proofs are scoped to a specific provider and permitted set IDs. Missing, expired or revoked metadata approval prevents publication. Separate art approval, the licensed-art runtime flag, exact HTTPS host allowlist and exact cleared asset URL are required to return an image URL. The boundary never fetches returned image URLs; any later image proxy needs its own network/redirect/DNS controls. Concrete adapters must honor the supplied AbortSignal; the default server deadline is eight seconds.

Provider records keep `source_id` and provider IDs separate from canonical UUIDs. Canonical import/mapping is a staff workflow, never a match inferred from card name or number alone. Unknown variant lists remain null. Returned data always requires curation; no provider payload can set a validated manifest, enable packs or introduce inventory availability.

Live vendor fetch adapters remain pending terms/access review and A's shared schemas. The normalization validator here is a B-private provider boundary, not a replacement for the required shared Zod/OpenAPI wire contract.
