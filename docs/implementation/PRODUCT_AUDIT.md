## External setup still required

Production Supabase has email confirmation enabled and uses the default sender. Direct provider diagnosis returned `over_email_send_rate_limit`; the dashboard confirms custom SMTP is not configured. Supabase's default email service is limited and restricted to project-team recipients. A verified sending domain and custom SMTP provider are required for dependable public signup and recovery. No confirmation bypass, auto-confirm workaround, purchased service or fabricated sender was introduced.

Configure the chosen provider in the project's Authentication → Emails → SMTP Settings. Keep SMTP credentials out of chat and source control. Then verify a new non-team address can receive confirmation, follow the link, sign in, request recovery and update its password. The application changes cannot replace this delivery configuration.

Primary reference: https://supabase.com/docs/guides/auth/auth-smtp

## Coverage and limits

Catalog/image requests, set indexes, individual cards and price endpoints were probed against production. Anonymous private/admin reads reject with 401; invalid bounds/cursors reject with 400. Disabled release/calendar sources return their intentional 503 rather than fabricated release data. Missing provider scans and unavailable prices remain explicit. This audit does not certify an exhaustive worldwide card database, hosted push delivery, market-pricing subscriptions, or scheduled privacy/notification worker operation.

The automated suite includes database migrations and RLS, account isolation, idempotent pack commits, physical/virtual separation, browser adapters and accessibility/responsive scans. Public signup and recovery are exercised against a disposable local Supabase, not another user's account. Real production email delivery remains unverified until SMTP is configured.
